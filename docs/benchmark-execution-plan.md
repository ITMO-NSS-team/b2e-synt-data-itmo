# План системы прогона эталонных бизнес-задач

## Команды проверки и прогона

После заполнения `deploy/.env` можно выполнить три уровня запуска.

```bash
# Все ready-кейсы: схема, данные, права, каталоги и условия эксперимента.
# Агент и LLM не вызываются.
make benchmark-check CASES=benchmarking/cases

# Два первых ready-кейса в порядке case_id, все выбранные режимы,
# один повтор. Это реальный вызов агента.
make benchmark-smoke CASES=benchmarking/cases

# Все ready-кейсы и три независимых повтора для каждой пары
# «кейс × режим».
make benchmark-run CASES=benchmarking/cases BENCH_REPETITIONS=3
```

`CASES` может указывать на каталог отдельных JSON-кейсов, один JSON или
собранный JSONL. Черновики со `status=draft` пропускаются. Если
`BENCH_DATA` не задан, используется `DATA_DIR` из локального `deploy/.env`; при
его отсутствии — `data-small`.

Другие параметры: `BENCH_MODES`, `BENCH_RESULTS`, `BENCH_EVAL_ID`,
`BENCH_TIMEOUT` и `BENCH_MODEL`. `BENCH_MODEL` меняет только model id в отдельной
pin-конфигурации benchmark; он не переключает провайдер или harness.
Доступ к модели определяется обычной конфигурацией стенда в `deploy/.env`.

Перед первым обращением к модели `benchmark-smoke` и `benchmark-run` проверяют
все выбранные пары «кейс × режим» и сверяют локальный снимок с фактическими
условиями работающего стенда. `benchmark-check` сохраняет `run-manifest.json` и
`preflight.json`. Полные прогоны дополнительно сохраняют `responses.jsonl`,
`scores.jsonl`, `summary.json` и отдельные файлы трасс в
`<BENCH_RESULTS>/<eval_id>/`.
Нулевая accuracy не ломает smoke: это измеряемый результат модели. Ненулевой
код возвращается при ошибке стенда, несовпадении условий или ненормализуемом
ответе.

## 1. Цель

Система должна запускать один и тот же набор эталонных бизнес-задач в трёх
режимах доступности навыков и сравнивать качество результата, корректность
отказов и стоимость решения по числу обращений к инструментам стенда.

Сравнивается именно влияние навыков. Во всех режимах агент сохраняет доступ к
данным Heimdall в пределах прав текущего пользователя.

## 2. Основные сущности

### BenchmarkCase

Одна эталонная бизнес-задача вместе с условиями выполнения и эталоном.

В текущей схеме поля разделяются на следующие группы:

| Группа | Поля |
| --- | --- |
| Идентификация | `schema_version`, `case_id`, `status`, `category` |
| Бизнес-задача | `query`, `source_type`, `source_business_process` |
| Пользователь | `employee_role`, `employee_id` |
| Состояние стенда | `snapshot_id` |
| Ожидаемый навык | `expected_skills` |
| Публичный формат ответа | `response_contract` |
| Скрытая оценка | `evaluation_contract` |
| Зафиксированное окружение | `skill_registry_hash` |

На этапе формирования набора кейс может иметь статус `draft`. Для такого кейса
допустимы `employee_id: null`, `response_contract: null` и
`evaluation_contract: null`: это означает, что структура уже создана, но
условия, формат результата или эталон ещё не материализованы.

Перед полноценным прогоном кейс должен перейти в состояние `ready`. К этому
моменту `employee_id`, `response_contract` и `evaluation_contract` должны быть
заполнены, а эталон должен соответствовать указанному `snapshot_id`. Способ их
автоматического заполнения не входит в текущий этап проектирования системы
прогона.

`response_contract` — публичная часть кейса. Она содержит версию общего
протокола ответа и JSON Schema поля `result` при успешном решении. Benchmark
добавляет единый конверт `result/message` и передаёт его агенту вместе с
`query`. Контракт не содержит категорию кейса, правильный исход, перечень
возможных исходов или эталонные значения.

`evaluation_contract` — закрытая часть кейса. Она содержит
`expected_outcome`, `gold_result` и правила сравнения. Она используется только
после прогона и никогда не передаётся агенту. Для категории `missing_skill`
ожидаемым исходом может быть как `answer` при допустимом решении базовыми
инструментами, так и `missing_skill`, если честный отказ является эталоном.

### SkillArtifact

Зафиксированный файл навыка в формате Heimdall:

- `recipe` — YAML с готовым `mcp_query`;
- `reference` — Markdown с последовательностью действий агента.

Сгенерированный навык подготавливается до оценочного прогона. Во время повторов
он не изменяется и не генерируется заново.

### RunMode

Конфигурация доступности навыков. Она задаёт разрешённые инструменты и каталог,
который видит агент.

### RunResult

Результат одного запуска одного кейса в одном режиме. Он содержит финальный
ответ, нормализованный результат, трассу инструментов, метрики и полный
отпечаток условий.

## 3. Режимы прогона

Название `none` не используется, потому что оно может ошибочно означать
отсутствие доступа к Heimdall. Режим без навыков называется
`skills_disabled`.

| Режим | Доступ к данным Heimdall | Доступ к навыкам | Назначение |
| --- | --- | --- | --- |
| `skills_disabled` | Да | Нет | Оценить решение без готового `recipe/reference`: агент выбирает доступную витрину и вызывает разрешённый `mcp_query` |
| `heimdall_skills` | Да | Стандартный каталог стенда | Измерить эффект существующих навыков Heimdall |
| `generated_skill` | Да | Стандартный каталог стенда с добавленным сгенерированным навыком | Измерить эффект навыка, полученного разрабатываемым методом |

### 3.1 `skills_disabled`

Агенту доступны инструменты для работы с сервисом и данными:

- `ToolSearch` — техническая загрузка разрешённых инструментов;
- `list_models` — поиск доступной витрины;
- `describe_model` — получение точных имён полей и метрик;
- `mcp_query` — разрешённый структурированный запрос данных к одной витрине;
- `get_docs` — документация по контракту Heimdall.

Инструменты `find_skills` и `get_skill` недоступны. Агент не видит каталог
`recipe/reference` и решает задачу только с помощью разрешённых инструментов
Heimdall. Он может выбрать витрину, получить её описание и заполнить допустимые
поля JSON-тела `mcp_query`.

Это не означает написание SQL, программы или скрипта. Произвольный код,
произвольный SQL, файловые инструменты и shell остаются запрещены во всех трёх
режимах. Тело `mcp_query` ограничено контрактом Heimdall и проверяется сервером
по зафиксированному каталогу витрин, колонок и метрик.

`get_docs` остаётся общей документацией интерфейса. Перед включением кейса в
набор необходимо проверить, что документация не содержит готового решения
именно этой бизнес-задачи. Иначе сравнение с режимами навыков будет
неоднозначным.

### 3.2 `heimdall_skills`

Агент получает тот же доступ к данным, а также:

- `find_skills`;
- `get_skill`;
- стандартный каталог `heimdall-skills`.

В этом режиме фиксируется версия стандартного каталога. Поле
`expected_skills` используется только оценочным контуром для проверки
маршрутизации и не передаётся агенту.

### 3.3 `generated_skill`

Агент получает тот же набор инструментов и тот же стандартный каталог, что и в
`heimdall_skills`. Перед запуском в реестр Heimdall дополнительно добавляется
заранее подготовленный сгенерированный навык. Таким образом можно проверить,
найдёт ли агент новый навык среди существующих и обратится ли именно к нему.

Правила режима:

- сгенерированный навык фиксируется до запуска;
- навык добавляется в стандартный каталог, а существующие навыки не удаляются и
  не заменяются;
- вычисляется хеш его содержимого и хеш итогового каталога;
- навык не должен изменять права, набор инструментов или данные стенда;
- имя сгенерированного навыка должно быть уникальным; совпадение с именем
  существующего навыка считается ошибкой подготовки режима;
- имя ожидаемого сгенерированного навыка фиксируется в конфигурации кейса или
  запуска и не передаётся агенту;
- все остальные навыки каталога остаются такими же, как в режиме
  `heimdall_skills`.

По трассе отдельно проверяются три события:

1. сгенерированный навык присутствовал среди результатов `find_skills`;
2. агент запросил его через `get_skill`;
3. после чтения навыка агент применил соответствующий `mcp_query` или
   инструкцию `reference` при решении задачи.

На текущем этапе сгенерированный артефакт может быть подготовлен вручную или
отдельным промптом. Это мок результата будущего метода генерации, но не мок
ответа Heimdall и не подмена результата `mcp_query`.

## 4. Общая схема работы

```text
набор BenchmarkCase
        │
        ▼
проверка структуры и выбор ready-кейсов
        │
        ▼
фиксация данных, модели, прав и каталогов
        │
        ├── skills_disabled
        ├── heimdall_skills
        └── generated_skill
        │
        ▼
новая сессия агента для каждого запуска
        │
        ▼
ответ + трасса инструментов + отпечаток условий
        │
        ▼
детерминированная оценка или LLM-as-judge
        │
        ▼
парное сравнение трёх режимов
```

## 5. План действий

### Этап 1. Зафиксировать контракт кейса

1. Принять текущий JSON как авторский формат `BenchmarkCase`.
2. Разрешить незаполненные значения для кейсов со статусом `draft`.
3. Определить отдельные правила допуска кейса со статусом `ready` к прогону.
4. Хранить каждый кейс отдельным JSON-файлом для удобства проверки и
   редактирования.
5. При запуске собирать выбранные кейсы в suite или JSONL без изменения
   исходных файлов.

### Этап 2. Зафиксировать конфигурации режимов

Для каждого режима необходимо явно сохранить:

- список доступных инструментов;
- путь и хеш каталога навыков;
- модель и температуру;
- версию системного промпта;
- снимок данных;
- настройки ловушек и задержек;
- конфигурацию прав пользователей.

Между режимами должны меняться только доступность и содержимое навыков.

### Этап 3. Подготовить каталоги навыков

1. Создать неизменяемый снимок стандартного каталога Heimdall.
2. Для `skills_disabled` полностью отключить канал `find_skills/get_skill`.
3. Для `heimdall_skills` использовать стандартный снимок каталога.
4. Для `generated_skill` скопировать стандартный снимок каталога и добавить в
   него целевые сгенерированные навыки.
5. Проверить отсутствие дубликатов имён и ошибок загрузки.

Генерация навыков и решение бизнес-задач являются разными фазами. Навык сначала
генерируется и фиксируется, а затем многократно оценивается.

В первой реализации снимки каталогов являются content-addressed: имя каталога
совпадает с SHA-256 его содержимого, а повторная проверка обнаруживает изменение
файлов. Канал навыков дополнительно фиксируется параметром
`skills_enabled`. Пока сгенерированных навыков нет,
`generated_skill` имеет `is_mock=true` и пропускается preflight со статусом
`mock_skipped`; фиктивный навык или фиктивный результат не создаются.

### Этап 4. Выполнить предварительную проверку

До обращения к LLM проверяются:

- валидность структуры кейса;
- готовность кейса к запуску;
- доступность указанного снимка данных;
- валидность `response_contract` и соответствие ему эталона из
  `evaluation_contract`;
- существование пользователя и соответствие его роли;
- загрузка стандартного и сгенерированного каталогов;
- валидность `recipe/reference`;
- существование используемых витрин, полей и метрик;
- полнота отпечатка экспериментальных условий.

Черновой кейс не считается ошибочным, но не включается в полноценный прогон.

### Этап 5. Выполнить прогоны

Для каждого кейса и режима:

1. Активировать нужную конфигурацию инструментов и каталога.
2. Создать новую изолированную сессию агента.
3. Детерминированно собрать сообщение агента из исходного `query`, общего
   протокола ответа и публичной схемы `result`. `evaluation_contract`, категория
   кейса и ожидаемый навык агенту не передаются.
4. Запустить решение задачи от имени указанного `employee_id`.
5. Сохранить исходный ответ и полную трассу инструментов.
6. Нормализовать финальный ответ в структуру, заданную `response_contract`.
7. Рассчитать метрики.

Каждая комбинация `case × mode` выполняется несколько раз. Для первичной
проверки достаточно одного повтора, для пилота — трёх, для итоговой оценки — не
менее трёх-пяти.

Порядок режимов следует перемешивать, чтобы временные изменения внешней среды
не были связаны с одним режимом.

#### Формирование сообщения агенту

Для `ready`-кейса `response_contract` обязателен. В авторском JSON хранится
компактная форма:

```json
{
  "protocol_version": "1.0",
  "result_schema": {
    "type": "array",
    "items": {
      "type": "object",
      "required": ["grade", "employee_count"],
      "properties": {
        "grade": {"type": "integer"},
        "employee_count": {"type": "integer", "minimum": 0}
      }
    }
  }
}
```

Функция `render_agent_query` добавляет к исходной формулировке одинаковое во
всех режимах описание исходов и полную JSON Schema ответа. В результате агент
видит бизнес-задачу и требование обязательно включить объект:

```json
{
  "result": "значение по result_schema либо null",
  "message": "краткое пояснение либо null"
}
```

Схема `result` описывает только форму успешного результата и не сообщает,
доступны ли данные и какой исход является правильным. Если результат получить
нельзя, агент возвращает `result: null` и объяснение в `message`, не размечая
свой ответ названием категории benchmark. Категория результата выводится
оценочным контуром из `result` и фактов трассы: например, 403 подтверждает
`access_control`, а успешный `mcp_query` с нулём строк — `no_data`. Хеш
публичного контракта, версия рендерера, исходный `query` и фактически
отправленное сообщение сохраняются в результате запуска. Это позволяет точно
воспроизвести prompt и проверить, что ни таксономия benchmark, ни эталон, ни
ожидаемый навык в него не попали.

Штатный системный prompt стенда может требовать свой структурированный хвост
`answer`. Это требование имеет более высокий приоритет, поэтому публичный
контракт не требует, чтобы benchmark JSON был единственным содержимым ответа.
Нормализатор детерминированно извлекает объект, соответствующий
`response_contract`, из составного ответа. В отдельной benchmark-конфигурации
системного prompt два формата позднее можно объединить, но это должно быть
зафиксировано новой версией prompt и одинаково применено ко всем режимам.

### Этап 6. Сохранить результат запуска

Параметры эксперимента, исходные ответы, оценки и итоговая сводка сохраняются в
разных файлах. Форматы описаны в разделе 6. Исходные результаты после прогона
не изменяются: повторная оценка создаёт новую версию файла с метриками.

`condition_id` полностью описывает конкретный режим. Для связи трёх запусков
одного кейса дополнительно используется `comparison_group_id`, в котором
зафиксированы одинаковые модель, пользователь, данные и параметры, но исключён
сравниваемый режим навыков.

### Этап 7. Оценить качество

Обязательные метрики первой версии:

| Метрика | Определение |
| --- | --- |
| `answer_accuracy` | Главная метрика: доля запусков, в которых задача решена правильно по применимому к категории критерию |
| `exact_match` | Совпадение `result` с `evaluation_contract.gold_result` по закрытым правилам `comparison` |
| `outcome_accuracy` | Доля ответов с правильным типом результата, который оценщик выводит из `result` и трассы, не запрашивая название категории у агента |
| `correct_refusal_rate` | Доля корректных отказов среди задач, для которых ожидается отказ |
| `generated_skill_loaded_rate` | Доля запусков режима `generated_skill`, в которых агент вызвал `get_skill` для ожидаемого сгенерированного навыка |
| `heimdall_calls` | Число всех обращений к инструментам Heimdall |
| `mcp_query_calls` | Число непосредственных запросов данных через `mcp_query` |
| `failed_tool_calls` | Число вызовов инструментов, завершившихся ошибкой или отказом |
| `total_tokens` | Суммарное число токенов за решение задачи |
| `latency_ms` | Полное время от отправки вопроса агенту до получения ответа |
| `agent_duration_ms` | Длительность хода агента из `b2e.turn.duration_ms` |
| `tool_time_ms` | Время, проведённое внутри вызовов инструментов, из `b2e.turn.tool_time_ms` |

Для одного запуска `answer_accuracy`, `exact_match` и `outcome_accuracy`
сохраняются как `0` или `1`. На уровне режима соответствующая метрика является
средним значением по всем применимым валидным запускам.

`answer_accuracy` рассчитывается единообразно, но критерий правильности зависит
от категории:

- для задачи с точным эталоном используется `exact_match`;
- для задачи с ожидаемым отказом проверяются тип и корректность отказа;
- для задачи без точного эталона используется результат LLM-as-judge.

LLM-as-judge получает бизнес-задачу, критерии оценки, ответ агента и допустимые
данные из трассы. Он оценивает выполнение задачи, полноту, обоснованность,
отсутствие выдуманных фактов, соблюдение прав и корректность неопределённости.
Judge не получает название режима и ожидаемый skill. Модель, версия промпта и
порог `pass` фиксируются в манифесте эксперимента.

### Этап 8. Сравнить режимы

Для каждого кейса рассчитываются парные различия:

```text
heimdall_skills − skills_disabled
generated_skill − skills_disabled
generated_skill − heimdall_skills
```

Основные итоговые показатели:

- абсолютные значения всех метрик по каждому режиму;
- абсолютная разница accuracy в процентных пунктах;
- относительное изменение accuracy;
- относительное уменьшение доли ошибок;
- относительное изменение числа вызовов, токенов и времени;
- `llm_judge_pass_rate` для задач без точного эталона.

Для метрики `M` относительное изменение режима `A` относительно режима `B`
вычисляется так:

```text
relative_change(A, B) = (M_A - M_B) / M_B
```

Для accuracy дополнительно рассчитывается абсолютное изменение:

```text
accuracy_delta_pp(A, B) = 100 × (accuracy_A - accuracy_B)
```

и относительное уменьшение доли ошибок:

```text
error_reduction(A, B) = ((1 - accuracy_B) - (1 - accuracy_A))
                        / (1 - accuracy_B)
```

Если знаменатель равен нулю, относительная метрика сохраняется как `null`.
Главным сравнением для оценки добавленного сгенерированного навыка является
`generated_skill − heimdall_skills`. Сравнение с `skills_disabled` показывает
эффект всего доступного каталога, а не только нового навыка.

Число вызовов инструментов следует сравнивать прежде всего среди корректно
решённых задач. Иначе отсутствие ответа с нулём вызовов ошибочно будет выглядеть
как наиболее эффективное поведение.

## 6. Форматы хранения результатов

Конфигурации, которые редактирует человек, можно хранить в YAML. Результаты
запусков и оценки сохраняются в JSON/JSONL, потому что этот формат проще
валидировать и обрабатывать автоматически.

```text
results/<eval_id>/
├── run-manifest.json
├── responses.jsonl
├── scores.jsonl
└── summary.json
```

### 6.1 `run-manifest.json`

```json
    "latency_profile": "instant"

      "skills_enabled": false,

    },
    "heimdall_skills": {
      "skills_enabled": true,
```

### 6.2 `responses.jsonl`

Неизменяемые исходные результаты. Одна строка соответствует одному запуску.
Запись содержит важные поля эталонной задачи, поэтому результат можно понять
без отдельного поиска исходного case-файла.

Минимальный снимок кейса включает: `category` — тип задачи и выбор оценщика,
`original_query` и `rendered_query`, публичный `response_contract`, скрытый
`evaluation_contract` и `expected_skills` для проверки маршрутизации.

```json
{
  "run_id": "case-0001-generated-01",
  "comparison_group_id": "case-0001-repetition-01",
  "case_id": "case-0001",

  "case_snapshot": {

    "original_query": "Покажи фактическую численность моей команды по грейдам",
    "rendered_query": "Покажи ... Формат ответа для автоматической проверки: ...",
    "employee_role": "manager",
    "employee_id": "...",
    "expected_skills": ["generated_skill_name"],
    "response_contract": {
      "protocol_version": "1.0",
      "result_schema": {"type": "array"}
    },
    "response_contract_hash": "sha256:...",
    "prompt_renderer_version": "benchmark-response-prompt@1",
    "evaluation_contract": {
      "expected_outcome": "answer",
      "gold_result": [],
      "comparison": {
        "ordered": false,
        "row_key": ["grade"],

        "numeric_absolute_tolerance": 0

    "raw_answer": "...",

    "found_skills": ["generated_skill_name"],
```

`evaluation_contract` и `expected_skills` доступны только оценочному контуру.
Агенту передаются `original_query` и публичный `response_contract`, объединённые
зафиксированным рендерером. Включение закрытого контракта в файл результата не
означает его включение в prompt.

### 6.3 `scores.jsonl`

Производные оценки. Они связываются с исходным результатом по `run_id` и могут

## 7. Размещение в проекте

На первом этапе бенчмарк размещается вместе со стендом:

```text
benchmarking/
├── cases/
├── skills/generated/
├── suites/
├── arms/
├── schemas/
└── results/
```

Существующий модуль `sim/skill_eval` можно использовать как основу раннера:
он уже создаёт сессии, получает трассы и сохраняет часть необходимых метрик.
Форматы кейсов, конфигурации режимов и результаты следует держать в отдельном
каталоге `benchmarking`, чтобы позднее вынести систему в самостоятельный
репозиторий без изменения логики эксперимента.

## 8. Минимальная последовательность реализации

1. Зафиксировать JSON-схему `BenchmarkCase` с поддержкой `draft`.
2. Описать три конфигурации режимов.
3. Описать схему `RunResult`.
4. Подготовить один `ready`-кейс и один мок сгенерированного навыка.
5. Выполнить smoke-прогон `1 кейс × 3 режима × 1 повтор`.
6. Проверить структурированное сравнение с эталоном и подсчёт вызовов.
7. Провести пилот на нескольких категориях задач.
8. После проверки добавить LLM-as-judge и выполнить полный прогон.
