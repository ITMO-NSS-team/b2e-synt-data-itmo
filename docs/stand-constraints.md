# Ограничения синтетического тестового стенда

Этот документ фиксирует границы стенда: что именно моделируется,
какие инструменты доступны агенту, какие источники данных считаются допустимыми
и как устроены права пользователя.

Короткая формула:

> Стенд моделирует один информационный сервис заказчика — Heimdall — на
> синтетическом HR-корпусе. Агент видит только выданные инструменты, каталог
> витрин и данные в пределах прав текущего сотрудника.

```text
пользователь
  роль: self / manager / hr
        │
        ▼
B2E-агент
  только разрешённые инструменты, без произвольного кода
        │
        ▼
Heimdall emulator
  каталог snapshot.json + проверка прав по X-Employee-Id
        │
        ├── синтетические витрины
        └── truth/ — эталонные ответы для проверки, агенту недоступно
```

**Оракул** в этом документе — не отдельная модель и не внешний сервис. Это
проверяющий контур стенда: код и данные, которые знают эталонный ответ на
тестовый вопрос и могут сказать, прав агент или нет. Поэтому `truth/` доступен
оракулу, но недоступен агенту.

## 1. Паспорт стенда


| Параметр                     | Зафиксированное значение                             |
| ---------------------------- | ---------------------------------------------------- |
| Моделируемый сервис          | один сервис: Heimdall, канал MCP v2                  |
| Предметная область           | HR-аналитика B2E-агента                              |
| Данные                       | полностью синтетический корпус                       |
| Дата снимка                  | `AS_OF = 2026-07-01`                                 |
| Каталог                      | `[catalog/snapshot.json](../catalog/snapshot.json)`  |
| Масштаб каталога             | 37 витрин, 7 схем, 4599 колонок, 148 метрик          |
| Навыки канала                | `[heimdall-skills/](../heimdall-skills/)`, только v2 |
| Скрытая истина               | `truth/`, не отдаётся через API                      |
| Внешние сервисы заказчика    | не моделируются                                      |
| Реальные персональные данные | отсутствуют                                          |


Стенд существует для воспроизводимых экспериментов. Поэтому у каждого прогона
есть отпечаток условий — `condition_id`. Это короткий идентификатор набора
настроек, при которых агент отвечал.

Если два прогона отличаются хотя бы одной важной настройкой, их нельзя
складывать как один эксперимент: агент мог стать лучше или хуже не из-за навыка,
а из-за другого набора инструментов, данных или прав.


| Что входит в отпечаток (`condition_id)` | Почему это важно                               |
| --------------------------------------- | ---------------------------------------------- |
| модель и температура                    | меняют поведение LLM                           |
| снимок данных                           | разные корпуса могут давать разные ответы      |
| `traps_enabled`                         | включает или выключает ловушки данных и канала |
| `latency_profile`                       | меняет задержки ответов эмулятора              |
| `hr_employee_ids`                       | определяет, кто видит всю компанию             |
| версия каталога навыков                 | меняет подсказки и рецепты, доступные агенту   |




### 1.1 Масштабы корпуса


| Корпус       | Назначение                      | Людей     | Подразделений |
| ------------ | ------------------------------- | --------- | ------------- |
| `data-small` | быстрые локальные проверки      | ≈ 2 741   | ≈ 540         |
| `data`       | полный исследовательский прогон | ≈ 294 000 | ≈ 32 500      |


Малый корпус удобен для разработки, но не доказывает свойства, зависящие от
масштаба: уникальность ключей, стоимость широких запросов, поведение больших
организационных деревьев.

### 1.2 Что сознательно не публикуется


| Компонент                  | Почему не открыт напрямую                                                                               |
| -------------------------- | ------------------------------------------------------------------------------------------------------- |
| `heimdall-emulator`        | личность задаётся заголовком `X-Employee-Id`; снаружи это позволило бы выдать себя за любого сотрудника |
| `truth/`                   | это эталон для проверки ответов, а не источник для агента                                               |
| sandbox исполнения навыков | это отдельная зона для одобренного кода, не пользовательский интерфейс                                  |


Наружу опубликованы только проксированные интерфейсы стенда: агент, research API,
админка, Phoenix и Telegram-бот. Эмулятор данных остаётся внутренним сервисом.

## 2. Инструменты агента

Главное ограничение: агент не может во время диалога написать строку кода и тут
же её выполнить. Это обеспечивается allowlist/denylist инструментов, а не просьбой
в промпте.

Где это в коде:


| Что смотреть                                        | Где                                                                           |
| --------------------------------------------------- | ----------------------------------------------------------------------------- |
| список известных Heimdall-инструментов              | `KNOWN_TOOLS` в `[sim/agent/tools.py](../sim/agent/tools.py)`                 |
| запрет файлов, сети и произвольной оболочки         | `DENIED_TOOLS` в `[sim/agent/claude_code.py](../sim/agent/claude_code.py)`    |
| выдача разрешённых инструментов конкретному прогону | `allowed_tools()` в `[sim/agent/claude_code.py](../sim/agent/claude_code.py)` |
| финальная denylist для запуска CLI                  | `denied_tools()` в `[sim/agent/claude_code.py](../sim/agent/claude_code.py)`  |




### 2.1 Карта инструментов


| Группа                | Инструменты                     | По умолчанию | Для чего                                        |
| --------------------- | ------------------------------- | ------------ | ----------------------------------------------- |
| Навигация по каталогу | `list_models`, `describe_model` | да           | найти витрину и точные имена полей              |
| Документация канала   | `get_docs`                      | да           | понять правила запроса, лимиты, фильтры, ошибки |
| Обзор каталога        | `get_overview`                  | нет          | увидеть общую карту навыков и доменов           |
| Данные                | `mcp_query`                     | да           | выполнить запрос к одной витрине                |
| Навыки Heimdall       | `find_skills`, `get_skill`      | да           | найти рецепт или справочный приём               |
| Загрузка MCP-схем     | `ToolSearch`                    | да           | технически подгрузить разрешённые инструменты   |
| Одобренный код        | `Bash(/opt/skills/run:*)`       | да           | запустить активный исполняемый навык по хешу    |


`AgentConfig.tool_subset` — это список Heimdall-инструментов, которые получает
конкретный прогон. По умолчанию агенту дают рабочий минимум:
`list_models`, `describe_model`, `get_docs`, `mcp_query`, `find_skills`,
`get_skill`.

Полный словарь знает ещё `get_overview`, но по умолчанию он не выдан. Это не
ошибка: `tool_subset` специально сделан экспериментальным рычагом. Так можно
запустить два условия и проверить, как меняется поведение агента, если дать ему
меньше или больше навигационных возможностей. При этом добавить произвольное
новое имя нельзя: если инструмента нет в `KNOWN_TOOLS`, конфигурация должна
упасть, а не молча выдать агенту неизвестную возможность.

### 2.2 Контракт вызова данных

Каждый вызов к эмулятору идёт от имени конкретного сотрудника:


| Заголовок                   | Роль в стенде                                |
| --------------------------- | -------------------------------------------- |
| `Authorization: Bearer ...` | технический сервисный токен                  |
| `X-Employee-Id`             | действующая личность, по ней считаются права |
| `x-heimdall-mcp-version`    | канал, по умолчанию `v2`                     |


Если `X-Employee-Id` отсутствует, стенд возвращает 403. Анонимные запросы не
моделируются.

Допустимые роли и права не лежат в этих заголовках текстом. Они вычисляются
сервером по `X-Employee-Id`: обычный сотрудник получает роль `self`, руководитель
подразделения — `manager`, сотрудник из `hr_employee_ids` — `hr`. Подробная
модель прав описана в разделе 4 и реализована в
`[sim/emulator/identity.py](../sim/emulator/identity.py)`.

REST-ручки вида `POST /api/v1/{schema}/{logic_model}/` существуют в эмуляторе, но
в набор инструментов агента не входят. Агент ходит через MCP.

### 2.3 Что запрещено по умолчанию

Режим по умолчанию: `code_execution = "forbidden"`.

Источник этой таблицы — `DENIED_TOOLS`, `allowed_tools()` и `denied_tools()` в
`[sim/agent/claude_code.py](../sim/agent/claude_code.py)`. То есть это не
документальное пожелание, а список, который реально передаётся в headless
Claude Code при запуске агента.


| Запрещённый класс        | Примеры                                       | Причина                                             |
| ------------------------ | --------------------------------------------- | --------------------------------------------------- |
| файловые инструменты     | `Read`, `Write`, `Edit`, `Glob`, `Grep`       | агент не должен читать корпус, `truth/` или конфиги |
| сеть                     | `WebFetch`, `WebSearch`                       | стенд моделирует закрытый контур                    |
| делегирование            | `Task`, `Agent`, `Skill`                      | иначе меняется субъект эксперимента                 |
| интерактивное разрешение | `AskUserQuestion`                             | в headless CLI такого инструмента нет               |
| произвольная оболочка    | `python3 -c`, `sh -c`, конвейеры, подстановки | обход запрета на код                                |


Попытка воспользоваться запрещённым инструментом попадает в `permission_denials`
трассы. Это измеряемый факт поведения агента.

### 2.4 Исключение: одобренный исполняемый навык

Единственная разрешённая оболочка в режиме по умолчанию:

```text
Bash(/opt/skills/run:*)
```

Она запускает не произвольную команду, а один фиксированный раннер одобренных
навыков. Исполняется только навык в состоянии `active`, по SHA-256 хешу кода.
Жизненный цикл описан в `[docs/agent-skill.md](agent-skill.md)`, раздел 2.

### 2.5 Экспериментальный режим `code_execution=allowed`

Этот режим существует только для проверки гипотезы «запрет кода ухудшает
качество». Он снимает файловые и shell-ограничения, но сеть остаётся закрытой.

Важно: это уже другое условие эксперимента. В контейнерной поставке корпус
смонтирован только в эмулятор; при локальном запуске из репозитория агент с
произвольным кодом может добраться до `truth/`, и такой прогон нельзя сравнивать
с обычным.

## 3. Каталог источников данных

Единственный источник имён витрин, колонок и метрик —
`[catalog/snapshot.json](../catalog/snapshot.json)`. Генератор корпуса, эмулятор
и валидаторы читают один и тот же снимок.

Где это в коде:


| Что                                               | Где                                                           |
| ------------------------------------------------- | ------------------------------------------------------------- |
| структура каталога (`Catalog`, `Model`, `Member`) | `[heimdall/catalog/model.py](../heimdall/catalog/model.py)`   |
| список моделей и `describe_model`                 | `[heimdall/app.py](../heimdall/app.py)`                       |
| проверка тела `mcp_query` по каталогу             | `[heimdall/engine/compile.py](../heimdall/engine/compile.py)` |


Каталог здесь — это машиночитаемая опись **доступных данных**. Его можно представить как карту:

```text
schema.logic_model
  ├── description
  ├── columns[]
  ├── metrics[]
  └── time_dimensions[]
```

Например, `dm_core.employee_actual` означает: схема `dm_core`, витрина
`employee_actual`. Схема — это логическая группа витрин: кадровое ядро,
специальные HR-модели, recruitment, технические витрины и т.д.

Зачем каталог нужен:


| Задача                       | Как помогает каталог                                              |
| ---------------------------- | ----------------------------------------------------------------- |
| выбрать источник             | `list_models` показывает доступные `schema.logic_model`           |
| не угадывать поля            | `describe_model` отдаёт точные `columns` и `metrics`              |
| проверить запрос             | `compile_query` сверяет тело с каталогом                          |
| зафиксировать границы стенда | если витрины или поля нет в снимке, агент не должен обещать ответ |


Практические следствия ниже — **не полный список правил** `mcp_query`. Это
короткая выжимка именно из устройства каталога: что следует из того, что все
источники данных описаны заранее в `snapshot.json`. Полный контракт запроса
описан дальше, в разделе 5.


| Следствие из каталога                       | Откуда следует                                                            | Что будет при нарушении                                 |
| ------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------- |
| имена берутся только из `describe_model`    | `describe_model` отдаёт `columns` и `metrics`; `compile_query` сверяет их | `unknown-column` или `unknown-metric`                   |
| `columns` и `metrics` — разные списки       | в `Model` это разные словари: `columns` и `metrics`                       | метрика в `columns` или колонка в `metrics` отклоняется |
| схема `system` скрыта                       | `HIDDEN_SCHEMAS = {"system"}`                                             | в `list_models` её нет, запрос даёт `model-not-found`   |
| один `mcp_query` обращается к одной витрине | тело запроса содержит одну пару `schema` + `logic_model`                  | JOIN между витринами отсутствует                        |
| новые витрины не создаются во время прогона | эмулятор читает фиксированный `catalog/snapshot.json`                     | каталог фиксирован снимком                              |


Остальные ограничения — права пользователя, лимиты, режим истории, пагинация,
бюджет памяти и каверзы — идут не из таблицы каталога, а из других частей
стенда. Они описаны отдельно в разделах 4–6.

### 3.1 Схемы каталога

Схема каталога — это верхний уровень группировки витрин. Она не задаёт права
сама по себе во всех случаях, но помогает понять, из какого слоя данных пришла
витрина.


| Схема         | Витрин | Доступность                                         | Описание                                                     |
| ------------- | ------ | --------------------------------------------------- | ------------------------------------------------------------ |
| `dm_core`     | 14     | все роли, строковый скоуп где применимо             | основной кадровый профиль, оргструктура, позиции, кандидаты  |
| `dm_special`  | 7      | все роли, кроме `talent_radar_people` только для HR | компетенции, признаки оттока, цифровой след, внешние профили |
| `stable`      | 3      | все роли, строковый скоуп где применимо             | уровни агентных навыков, расшифровки, КЛАДР                  |
| `sset`        | 1      | все роли                                            | справочник должностей                                        |
| `anagent`     | 7      | только HR                                           | устаревшие копии, эмбеддинги, синтетический подбор           |
| `recruitment` | 4      | только HR                                           | заявки и публикации вакансий                                 |
| `technical`   | 1      | все роли                                            | специально пустая витрина                                    |




### 3.2 Витрины по группам

В полной таблице ниже флаги читаются так:


| Флаг     | Значение                                 |
| -------- | ---------------------------------------- |
| `ист.`   | поддерживает режим истории               |
| `HR`     | закрыта для `self` и `manager` целиком   |
| `устар.` | `_dep`-копия, `deprecated: true`         |
| `пусто`  | объявлена пустой через `EMPTY_BY_DESIGN` |

#### HR-only и служебные витрины

Эти источники либо закрыты для обычных сотрудников и руководителей, либо являются
служебными. Они важны для проверки прав доступа: агент должен получить 403 там,
где его действующая личность не имеет HR-роли.


| Адрес                                      | Назначение                    | Флаги            |
| ------------------------------------------ | ----------------------------- | ---------------- |
| `anagent.employee_actual_dep`              | устаревшая копия профиля      | HR, устар.       |
| `anagent.employee_actual_orion_dep`        | устаревшая краткая копия      | HR, устар.       |
| `anagent.employee_hist_dep`                | устаревшая история            | HR, устар., ист. |
| `anagent.oss_ebase_embs`                   | эмбеддинги                    | HR               |
| `anagent.oss_ebase_embs_dep`               | устаревшие эмбеддинги         | HR, устар.       |
| `anagent.skills_ebase_embs_dep`            | устаревшие эмбеддинги навыков | HR, устар.       |
| `anagent.recruitment_sint`                 | синтетический подбор          | HR               |
| `recruitment.job_requisition_large`        | заявки                        | HR               |
| `recruitment.publication`                  | публикации вакансий           | HR               |
| `recruitment.publication_extract`          | извлечения из публикаций      | HR               |
| `recruitment.publication_extract_enriched` | обогащённые извлечения        | HR               |
| `technical.memai_memmcp_config`            | витрина без данных по замыслу | пусто            |


Особые случаи — это витрины или группы витрин, которые легко прочитать неверно по
одному названию. Их лучше зафиксировать отдельно, чтобы навык не делал ложных
обещаний.


| Случай                                 | Как трактовать                                                                                   |
| -------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `technical.memai_memmcp_config` пустая | это проверяемое свойство корпуса, а не недоделка                                                 |
| `_dep`-витрины                         | устаревшие копии, покрывают около 82% людей; новые запросы лучше направлять в актуальные витрины |
| `position_hist`                        | имя похоже на историческое, но `is_history = false`                                              |
| `churn_model_metrics`                  | содержит признаки оттока; в API нет готового риска или вероятности ухода                         |




### 3.3 Ключи личности

Один и тот же человек намеренно появляется под разными ключами. Канал сам их не
склеивает.


| Ключ                               | Где встречается             | Что важно                          |
| ---------------------------------- | --------------------------- | ---------------------------------- |
| `person_id`                        | основные кадровые витрины   | UUID                               |
| `employee_id`                      | кадровые витрины            | табельный номер                    |
| `emp_key`                          | составные ключи             | кортеж `(компания, табельный)`     |
| `tn`, `tab_num`, `employee_number` | отдельные витрины и фильтры | табельный в другом имени           |
| внешний `id`                       | `talent_radar_people`       | чужое пространство идентификаторов |


Фильтр по `employee_id` на витрине, которая ключуется только `person_id`, может
вернуть пусто. Это не означает, что человека нет в корпусе.

### 3.4 Данные, которых агент не видит


| Что недоступно через API                                  | Где существует       | Для чего используется                     |
| --------------------------------------------------------- | -------------------- | ----------------------------------------- |
| `ability`, `potential`, `engagement`, `conscientiousness` | `truth/people.json`  | эталон и генерация наблюдаемых признаков  |
| gold-метки, включая `attrition_risk`                      | `truth/`, оракул     | автоматическая проверка ответов           |
| поля с суффиксом `_hidden`                                | не попадают в снимок | защита от утечки скрытых факторов         |
| произвольный SQL                                          | отсутствует в канале | запросы строятся только через `mcp_query` |
| новые точки входа API                                     | отсутствуют в стенде | каталог фиксирован                        |


Рецепт `[heimdall-skills/attrition/attrition_features.yaml](../heimdall-skills/attrition/attrition_features.yaml)`
формулирует это прямо: признаки оттока — это не прогноз и не право ранжировать
людей по риску ухода.

## 4. Модель прав доступа

Права применяются на стороне эмулятора. Агент не решает сам, можно ли ему смотреть
данные: запрос либо проходит, либо получает 403, либо автоматически ограничивается
строками доступного скоупа.

### 4.1 Роли


| Роль      | Кто получает                   | Что видит                         |
| --------- | ------------------------------ | --------------------------------- |
| `self`    | обычный сотрудник              | только свою запись                |
| `manager` | руководитель подразделения     | своё подразделение и все дочерние |
| `hr`      | сотрудник из `hr_employee_ids` | всё, включая HR-only схемы        |


Роль выводится из `employee_id` и снимка данных. Текст вопроса её не меняет.
Неизвестный `employee_id` даёт 403 `auth-failed`.

`hr_employee_ids` входит в отпечаток прогона. Это принципиально: HR и руководитель
получают разные ответы на один и тот же вопрос о компании.

### 4.2 Как принимается решение

```text
запрос пришёл без X-Employee-Id?
        └── 403 forbidden

employee_id отсутствует в снимке?
        └── 403 auth-failed

модель HR-only, а роль не hr?
        └── 403 forbidden

запрос явно называет человека вне скоупа?
        └── 403 forbidden

иначе:
        └── к запросу добавляется фильтр скоупа, затем выполняется mcp_query
```



### 4.3 Что закрыто целиком


| Закрытая область                 | Для кого закрыта  |
| -------------------------------- | ----------------- |
| `anagent.*`                      | `self`, `manager` |
| `recruitment.*`                  | `self`, `manager` |
| `dm_special.talent_radar_people` | `self`, `manager` |


HR видит эти модели без строкового ограничения.

### 4.4 Ответы на типовые ситуации


| Ситуация                                          | Ответ стенда                   | Почему                           |
| ------------------------------------------------- | ------------------------------ | -------------------------------- |
| нет `X-Employee-Id`                               | 403 `forbidden`                | анонимный доступ не моделируется |
| `employee_id` не из снимка                        | 403 `auth-failed`              | такой личности нет               |
| менеджер читает `recruitment.*`                   | 403 `forbidden`                | схема только для HR              |
| сотрудник фильтрует по чужому `person_id`         | 403 `forbidden`                | явная попытка выйти из скоупа    |
| менеджер делает широкий запрос без person-фильтра | 200, но только его дерево      | эмулятор добавляет фильтр скоупа |
| HR делает широкий запрос                          | 200 без строкового ограничения | роль видит всё                   |


Ключи скоупа разделены по типам: `person_id` — UUID, `employee_id` — табельный.
Смешивать их в одном `IN` нельзя: это даст `filter-value-invalid`.

## 5. Ограничения `mcp_query`

`mcp_query` — структурированный запрос к одной витрине Heimdall. Это не SQL:
агент заполняет разрешённые поля JSON-тела, а сервер сам проверяет каталог,
собирает план и возвращает данные.

Для навыков это важный контракт. Если рецепт содержит поле `query`, то внутри
него должно лежать именно тело `mcp_query`: допустимые поля, существующая витрина,
существующие колонки и метрики. Поэтому этот же момент отдельно отмечен в
`[docs/agent-skill.md](agent-skill.md)`, в разделе про рецепт.

### 5.1 Из чего состоит тело запроса


| Поле                             | Зачем нужно                                           |
| -------------------------------- | ----------------------------------------------------- |
| `schema`, `logic_model`          | адрес одной витрины                                   |
| `columns`                        | колонки для выдачи; в агрегате — ключи группировки    |
| `metrics`                        | метрики каталога для агрегата                         |
| `param_columns`, `param_metrics` | параметрические члены каталога                        |
| `filters`                        | дерево условий                                        |
| `order_by`                       | сортировка                                            |
| `limit`, `offset`                | постраничная выдача                                   |
| `limit_by`                       | ограничение top-N внутри групп; не работает в истории |
| `time_dimensions`                | включает исторический режим                           |


Обязательны только `schema` и `logic_model`, но запрос должен что-то возвращать:
`columns`, `metrics`, `param_metrics` или `time_dimensions`. Иначе будет
`query-empty`.

Любое поле вне этого списка отклоняет весь запрос (`request-validation-error`).

### 5.2 Что такое режим запроса

Режим — это способ, которым Heimdall понимает одно и то же тело запроса: вернуть
строки, посчитать агрегат или построить историю. Отдельного поля `mode` нет,
поэтому режим определяется по тому, какие поля присутствуют в теле.


| Как выглядит тело                     | Режим       | Что это значит                                       |
| ------------------------------------- | ----------- | ---------------------------------------------------- |
| есть `time_dimensions`                | `history`   | вернуть значения по периодам                         |
| есть `metrics` или `param_metrics`    | `aggregate` | посчитать метрики; `columns` становятся группировкой |
| есть только `columns`                 | `rows`      | вернуть плоские строки без агрегации                 |
| нет ни колонок, ни метрик, ни истории | ошибка      | нечего возвращать: `query-empty`                     |


Пример: если в запросе есть `columns: ["department"]` и `metrics: ["headcount"]`,
это агрегат по подразделениям. Если оставить только `columns`, это уже не счёт,
а список строк.

### 5.3 Ограничения запроса

Это полный список ограничений канала, важных для навыка. Технические ошибки
валидации отдельных полей перечислены в справке `errors`, но смысловые границы
канала такие:


| Ограничение                                                     | Что из этого следует                                             |
| --------------------------------------------------------------- | ---------------------------------------------------------------- |
| один запрос обращается к одной витрине                          | JOIN между витринами отсутствует                                 |
| произвольного SQL нет                                           | агент не пишет `SELECT`, а заполняет JSON-тело                   |
| произвольных агрегатов нет                                      | доступны только метрики из каталога                              |
| имена полей только из `describe_model`                          | угадывание колонок и метрик отвергается                          |
| `columns` и `metrics` не взаимозаменяемы                        | колонка не считается метрикой, метрика не выводится как колонка  |
| история есть не у всех витрин                                   | `time_dimensions` работает только у четырёх моделей              |
| актуальные витрины не дают произвольный срез на дату            | у них есть только текущий снимок                                 |
| год к году не выражается одним запросом                         | корпус зафиксирован на одном `AS_OF`                             |
| `Array(Tuple)` и `Array(Map)` нельзя фильтровать и группировать | такие поля можно только вывести                                  |
| массивы одного блока позиционно связаны                         | i-й элемент `goals.*` относится к i-му элементу других `goals.*` |
| `limit` ограничивает выдачу, а не стоимость чтения              | широкий запрос остаётся дорогим даже при маленьком `limit`       |




### 5.4 Исторический режим

Факт историчности берётся из `is_history` в каталоге, а не из суффикса `_hist`.  
Например, `position_hist` выглядит исторической, но режим истории не поддерживает.


| Историческая витрина        | Что можно делать              |
| --------------------------- | ----------------------------- |
| `anagent.employee_hist_dep` | получать значения по периодам |
| `dm_core.candidate_hist`    | получать значения по периодам |
| `dm_core.employee`          | получать значения по периодам |
| `dm_core.employee_hist`     | получать значения по периодам |


Окно истории задаётся явно: `from`, `to`, гранулярность (`day`, `week_end`,
`month_end`, `quarter_end`, `year_end`). Относительных окон вроде «за последние
12 месяцев» нет — их нужно заранее превратить в конкретные даты. Глубина истории
ограничена пятью годами.

В истории не работают `limit_by`, `param_columns` и `param_metrics`.

### 5.5 Лимит, страницы и подсчёт

Таблица ниже отвечает на вопрос «сколько строк вернёт один вызов». Правила после
неё отвечают на вопрос «как по этим страницам не сделать неверный вывод».


| Параметр             | Значение                                           |
| -------------------- | -------------------------------------------------- |
| `limit` по умолчанию | 100                                                |
| максимум MCP         | 1000                                               |
| `offset`             | сдвиг страницы                                     |
| `has_next_page`      | признак, что есть следующая страница               |
| `limit` в ответе     | применённое значение, а не обязательно запрошенное |


Если `traps_enabled=true`, `limit > 1000` молча ужимается до 1000. Если
`traps_enabled=false`, тот же запрос получает `request-validation-error`. Это
различие относится к каверзам канала.

Практические правила:


| Ситуация                       | Правильное действие                                      |
| ------------------------------ | -------------------------------------------------------- |
| вернулось ровно 1000 строк     | считать выборку потенциально обрезанной                  |
| нужно обойти несколько страниц | задать стабильный `order_by`                             |
| нужно узнать численность       | использовать метрику в aggregate-режиме                  |
| хочется взять `len(data)`      | помнить, что это размер страницы, не размер всей выборки |




### 5.6 Бюджет памяти

Эмулятор читает данные поколоночно: если запрос упомянул колонку, она поднимается целиком по всей витрине. Поэтому `limit: 1` уменьшает число строк в ответе, но не делает чтение широкой витрины дешёвым.

Пример: запросить несколько нужных колонок из `employee_actual` нормально.
Запросить все сотни колонок той же витрины на полном корпусе может потребовать
гигабайты памяти ещё до формирования ответа.

Чтобы воркер не погибал от OOM, перед исполнением стоит гейт:


| Проверка                   | Значение              |
| -------------------------- | --------------------- |
| когда считается            | до чтения колонок     |
| код отказа                 | `query-too-expensive` |
| HTTP                       | 422                   |
| потолок по умолчанию       | 4 ГиБ                 |
| зависит от `traps_enabled` | нет                   |


Это не каверза и не поведение агента. Это ограничение самого стенда: слишком
широкий запрос должен получить измеримый отказ, а не уронить процесс.

## 6. Переключаемые каверзы

Каверзы нужны в этом документе только потому, что они являются частью
фиксированных ограничений стенда и меняют условие эксперимента. Это ситуации, где
сервис отвечает 200 OK, но наивная интерпретация результата ведёт к ошибке.

Подробный перечень каверз лежит в `[b2e/traps.py](../b2e/traps.py)` и
`[heimdall/engine/quirks.py](../heimdall/engine/quirks.py)`. Здесь фиксируется
только общий принцип:


| Тип            | Пример                                                           | Что проверяет                                                                  |
| -------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| каверзы данных | `NULL` как «не оценивался», устаревший флаг, верхний регистр ФИО | умеет ли агент не делать лишний вывод из плохого признака                      |
| каверзы канала | молчаливое ужатие `limit`, особенности `ILIKE`, порядок `NULL`   | умеет ли агент читать контракт ответа и не принимать 200 OK за гарантию смысла |


`traps_enabled=false` выключает каверзы канала и требует отдельный снимок корпуса
без каверз данных. Это другое экспериментальное условие; поэтому оно уже входит
в `condition_id`, описанный в начале документа.
